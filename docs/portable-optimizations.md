# 通用 C 执行与扫描线复用

本文描述便携 C 优化路径。可选的 `GBA_DYNAREC` 具有独立的宿主和执行内存要求，
见 [ARM32 动态重编译](dynarec.md)；开启时不再使用本文的寄存器预解码块缓存。

所有新增执行、等待识别和绘制复用代码使用 C11，不依赖 RT-Thread、ARM
汇编、可执行内存、宿主 JIT 或游戏地址表。同步基准为 `e0f44c6`，来源和逐文件摘要保存在
[optimization-sync.json](optimization-sync.json)。

`GBA_FAST_CPU=1` 启用按最近设备事件限制的 CPU 执行片段，以及 ROM、
IWRAM、EWRAM 的实时取指页。页缓存保存当前字节的地址，没有复制解码后
的旧指令；自修改 RAM、镜像地址、页边界、GPIO、BIOS 和流式 ROM 保留各自
的访问语义。寄存器结果、进位、溢出、流水线和事件同步仍可与原核心对比。

`GBA_FAST_WAIT=1` 依赖上述执行器。只有无写入的完整循环返回相同 CPU、
流水线、预取和总线状态，才能重复其整轮周期；终点严格早于设备事件、
计时器下次计数变化和调用者的运行预算。寄存器写入、DMA 写内存、异常、
模式切换、显示状态变化及公共运行/恢复边界会使证明失效。数学循环连续
失败后暂时停止尝试，减少识别本身的耗时。读取值的摘要仅决定重试策略，
不会被用作跳过循环的正确性证明。

`GBA_VIDEO_CACHE=1` 使用完整 framebuffer 复用没有变化的扫描线。行键逐
字节比较渲染寄存器、仿射参考值、背景延迟和窗口，不使用可能碰撞的摘要。
VRAM 以 32 字节、调色板以 8 字节记录反向行依赖；实际写入只使曾读取该块
的行失效。依赖集合保守累积，可能多画行，不会漏画。OAM 几何和内容变更
标记精灵前后覆盖的行，矩阵变更标记全部行，并在硬件锁存时才提交失效。
时序、DMA、IRQ、每帧输出和音频继续执行。半屏配置自动停用行复用。

启用行复用的调用者应持有视频内存，并在直接编辑借用的 VRAM、调色板、
OAM、framebuffer 或机器 OAM 锁存后调用 `gba_video_invalidate()`。通过
核心 CPU/DMA 路径的写入、复位、成功恢复状态由核心自动处理。关闭该选项
时，调用此函数没有效果。行键和有界依赖表增加约 85 KiB 派生实例空间，不扩大
GBA 硬件 RAM 或 GAST v7；CPU 片段和等待记录同样不进入存档。

framebuffer 修订号在重新绘制行、复位和恢复/外部失效时推进，并在最大值
饱和。端口分别记录两个显示缓冲的修订号：已复制且内容未变的缓冲可以
直接重新排入 vblank 队列；其余缓冲先清边/缩放/复制并清数据缓存。修订号
饱和后总是复制，恢复时也重新建立两个缓冲的身份。呈现每个模拟帧的计数
与节拍不省略。

上述选项可通过编译定义或平台 `gba_conf.h` 设置。必须让全部核心与端口
翻译单元使用相同配置。`GBA_TEST_MODE=1` 为逐指令跟踪停用等待跳过和行
复用；对应的无跟踪游戏回放和随机绘制场景另行验证这些路径。该配置是
静态的诊断选择，运行时没有精度/速度双模式。

固件中的采样探针、旧等待实验、原生 IO 与 LTO 实验保持独立，并默认关闭。
主机结果只能证明回归和等价性；实机 FPS、音频补零及内存数据见工程的
性能报告与原始 UART。

`GBA_FAST_ALU=1` 依赖 `GBA_FAST_CPU=1`：只对白名单内不访存、不跳转、
不修改模式的连续 ARM/Thumb 寄存器指令，批量执行到最近硬件事件之前。
指令仍逐条运算，取当前 ROM/IWRAM 字节，完整保留条件执行、流水线、
开放总线、WAITCNT 顺序/非顺序等待和预取 FIFO 的成本。访问 GPIO、ROM
末尾/区域边界、控制/存储指令、DMA 或 IRQ 到达时回退通用执行器。
它减少执行包装调用，不依赖特定游戏，不省略乘法或改变运算结果。
肩键、存档、音频和 RT-Thread 显示队列属于独立的固件端口。

通用核心选项默认均为 0，由平台配置选择。本仓库 `xmake f --fast_core=y` 启用已验证的组合；RT-Thread 端采用相同组合。

关闭整个 `fast_core` 构建选项可恢复原默认配置；独立指定宏时，关闭 CPU
批量执行也须关闭等待、寄存器片段和指令块。非法组合拒绝编译。
生产不启用测试跟踪/采样，原核仍保留扫描线精度和原有快速策略。

## IWRAM 运算块预解码

`GBA_FAST_BLOCKS=1` 依赖 `GBA_FAST_CPU=1` 与 `GBA_FAST_ALU=1`。
缓存 64 个最多 16 条 ARM 寄存器指令的块，实例派生空间增加 21 KiB。
只覆盖 IWRAM 中已对齐的纯运算；存储、设备访问、模式/控制变化和 Thumb
继续经过原执行路径。每次使用核对两个已预取指令和当前 RAM 的完整后续
字节，因此无需外部失效 API，也能发现 DMA、自修改、镜像与恢复状态修改。
未变化代码只复用解码结果，寄存器值、条件执行、乘法周期和标志位仍实时
计算。流水线和开放总线集中在事件前的块边界提交，不省略客体周期。
缓存不进入 GAST v7；其有效性依赖完整字节核对，不能用摘要代替核对。
寄存器、存储、显示和音频结果不能以精度取舍掩盖。

本轮普通读取扩展与乘法融合实机未达到门槛，已撤回；通用核心保留一个
执行实现，平台可在编译时关闭缓存。生产关闭测试跟踪和探针。

## 仓库构建与验证

默认关闭新增可选缓存，保留原有内存预算。根目录 xmake 工程启用方式：

```powershell
xmake f -m release --fast_core=y -y
xmake build
pwsh -File test/run.ps1 -SkipFetch -FastAcceptance -FastCore
python test/optimization_check.py --cc gcc
python test/optimization_replay.py --cc gcc --rom-directory /path/to/local/roms --frames 900
pwsh -File test/cross.ps1
```

`--cc` 可传编译器绝对路径，或设置 `CC` 环境变量。回放工具使用本地四个
ROM：`metroid_fusion.gba`、`mario_advance.gba`、`zelda_minish.gba`、
`pokemon_emerald.gba`；以 Git 中固定 `e0f44c6` 为对照，独立临时副本比较
原核心、优化和 LTO 的画面、PCM、周期、CPU 和 GAST v7，原 ROM/存档不改写。
未附带或下载商业 ROM。测试需 Python 3.12+、Git 与支持 LTO 的 GCC。

`optimization_check.py` 不开启逐指令跟踪，覆盖 128 场景/32768 执行边界、
真实 IRQ、DMA 自修改、PC/寄存器移位/乘法，以及 80 个取指边界场景、
96 个绘制场景/1540 变体。常规 FastAcceptance 的跟踪不能代替这些测试。

编译器或指令块缓存可能调用标准 C `memcpy`/`memcmp`/`memset`。裸机无 libc
链接时需提供等价函数；`test/mcu_smoke.c` 展示不分配堆的实现。
`cross.ps1` 额外验证完整优化组合在 Cortex-M4 的静态链接；这不是该 MCU
的运行或性能验证。历史 `GBA_PORT_BATCH_EVENTS`/`GBA_PORT_FAST_RUN` 命名
表示纯 C 事件调度选项，不引入平台依赖。原生 IO、旧等待实验和探针不启用。

固件 LCD 缓冲复用、2 倍缩放和音频队列仍属于独立端口，不放入核心。
本次同步未重新进行板测，板端数据引用同步前已封存的同字节核心结果，
见 [同步验证](optimization-sync-validation.md)。
